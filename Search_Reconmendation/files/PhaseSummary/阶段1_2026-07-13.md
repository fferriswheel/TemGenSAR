# 阶段1_2026-07-13：Dynamic / Time-aware SID 文献阅读与方法收束

## 1. 本阶段讨论目标

本阶段承接阶段0的结论，重点从“选题是否有空间”转向“已有 dynamic / stale / time-aware SID 方法具体怎么做，以及这些工作对我们的 Search-Recommendation 部分共享 SID 有什么启发”。

本阶段重点阅读和讨论了三类相关工作：

1. `Mitigating Collaborative Semantic ID Staleness in Generative Retrieval`
2. `ChronoID: Infusing Explicit Temporal Signals into Semantic IDs for Generative Recommendation`
3. `SSRLive: Live Streaming Recommendation with Dynamic Semantic ID`

阶段0中已经判断：

```text
单纯提出 shared prefix + task-specific suffix 的静态 SID 结构创新性不足。
```

本阶段进一步明确：

```text
纯 recommendation 场景中的 dynamic SID / stale SID 已经有较多相关工作。
```

因此，我们的后续方向不能泛化为：

```text
Dynamic Semantic IDs for Generative Recommendation
```

更合适的定位应是：

```text
Dynamic maintenance of partially shared Semantic IDs for unified generative search and recommendation.
```

也就是把 dynamic SID 应用到 search-rec 共享 SID 结构中，研究在 temporal drift 下如何局部刷新 shared prefix / task-specific suffix，并诊断 search 与 rec 两个任务之间的漂移一致性和冲突。

## 2. Mitigating Collaborative Semantic ID Staleness in Generative Retrieval

### 2.1 任务设置

该工作关注的是 recommendation candidate generation，而不是 search-rec 联合任务。

基本任务是：

```text
给定用户历史交互序列 H_u，生成下一个 item 的 Semantic ID。
```

形式上可以理解为：

```text
Input:
  user history = [SID_{i1}, SID_{i2}, ..., SID_{in}]

Output:
  next item SID = [c1, c2, ..., cm]
```

模型不是预测一个 session-level 序列，而是预测未来的一个 item。生成式推荐模型通过自回归方式生成该 item 的 SID token 序列。

### 2.2 历史交互与 ground truth

历史交互序列 `H_u` 通常来自用户按时间排序的 item interactions。

在公开推荐数据中，这类 interaction 可能是：

- review；
- rating；
- click；
- view；
- purchase；
- long-view；
- like / comment 等。

具体取决于数据集。对 Amazon Reviews 这类数据而言，常见的是用户的 review / rating 序列；对短视频或新闻数据而言，则可能包含 click、view、long-view 等多种反馈。

ground truth 是用户在历史序列之后真实交互的下一个 item：

```text
H_u = [i1, i2, i3, i4]
target = i5
ground truth SID = SID_{i5}
```

模型生成 top-K SID 后，再映射回 item，计算推荐指标。

### 2.3 Top-K SID 生成与指标

生成式模型按 token 自回归生成 SID：

```text
P(SID_i | H_u) = Π_t P(c_t | H_u, c_<t)
```

候选 SID 的分数通常是 token log-probability 之和：

```text
score(SID_i) = Σ_t log P(c_t | H_u, c_<t)
```

top-K item 可通过 constrained beam search 或 trie-constrained decoding 得到，保证生成结果是合法 SID。

常用指标：

```text
Recall@K = 1{ground truth item appears in top-K}
```

对单一 ground truth 的 next-item prediction，用户级 Recall@K 就是 top-K 是否命中目标 item，然后对所有用户取平均。

`nDCG@K` 考虑命中位置：

```text
nDCG@K = 1 / log2(rank + 1), if rank <= K
       = 0, otherwise
```

其中 `rank` 是 ground truth item 在 top-K 结果中的位置，从 1 开始。

### 2.4 核心问题：SID staleness

该论文指出，基于 collaborative signals 构造的 SID 会随时间变旧。

原因是：

```text
item 的协同关系、用户兴趣、交互分布都会变化。
```

如果一直使用旧 SID，生成模型面对新行为分布时性能会下降。但如果直接重建所有 SID，又会导致：

- 旧 checkpoint 无法直接复用；
- SID token label 发生大规模重排；
- 模型需要重新学习 token 到 item 的映射；
- full retraining 成本高。

### 2.5 方法核心

该工作的核心不是显式给 item 加时间 token，而是解决：

```text
如何刷新 collaborative SID，同时尽量兼容旧模型。
```

大致流程为：

```text
1. 按时间划分训练 block。
2. 在新时间 block 上根据最新 interaction 重新构造 collaborative SID。
3. 新旧 SID token label 之间做对齐。
4. 用对齐后的 SID warm-start 旧 checkpoint。
5. 进行轻量 finetune。
```

其中关键在于 token alignment。它试图让新 SID 的 token 尽量复用旧 token label，使模型原来学到的 token embedding 和 decoder 分布仍然有意义。

可以理解为：

```text
raw new SID:
  item A -> [8, 21, 3]

after alignment:
  item A -> [2, 15, 7]
```

对齐后的 token label 不一定保留新聚类的原始编号，而是优先保持与旧 SID 空间的兼容。

### 2.6 对我们的启发

这篇文章对我们的价值主要在于：

1. 证明 SID staleness 是一个真实且重要的问题。
2. 说明 SID refresh 不能只看新 SID 是否更好，还要考虑 checkpoint compatibility。
3. 提供了 token alignment / warm-start 的技术借鉴。

但它的边界也很清楚：

```text
它主要处理 recommendation-only collaborative SID refresh。
```

它没有处理：

- search 与 rec 共享 SID；
- shared prefix 与 task suffix 的局部刷新；
- search 刷新是否破坏 rec；
- rec 刷新是否破坏 search；
- 两个任务漂移方向是否一致。

因此，我们不能把贡献写成普通 stale SID mitigation，而应强调：

```text
search-rec partially shared SID 下的结构化、任务感知 refresh。
```

## 3. ChronoID / Time-aware SID

### 3.1 任务设置

ChronoID 关注的是将显式时间信号注入 Semantic ID，用于 generative recommendation。

它仍然主要是 recommendation 场景：

```text
Input:
  user history with temporal information

Output:
  next item SID
```

它关注的问题是：

```text
传统 Semantic ID 多由 item text / metadata / interaction 表示生成，
但没有显式建模用户与 item 交互发生的时间。
```

### 3.2 时间信息如何加入

本阶段重点澄清了 ChronoID 的时间注入方式。

它使用两类时间信号：

1. absolute time：

```text
t_ui = Unix timestamp of user u interacting with item i
```

2. relative time：

```text
Δt_ui = t_ui - t_u,i-1
```

其中 `Δt_ui` 表示用户本次交互与上一次交互之间的时间间隔。

时间值经过 sinusoidal embedding 转成向量。论文中提到的维度设置大致是：

```text
time embedding: 768
text embedding: 2560
```

然后将时间 embedding 与 item text embedding 融合。

### 3.3 三种融合方式

ChronoID 讨论了几类时间融合方式。

#### Early Fusion

先把 item text embedding 和 time embedding 拼接或融合，再送入量化器：

```text
e_i = Fuse(text_i, time_ui)
SID = RQ-VAE(e_i)
```

直觉是让 item 的语义表示在量化之前就带有时间上下文。

#### Late Fusion

先得到 item SID，再额外加入 temporal SID：

```text
SID = [item token 1, item token 2, item token 3, temporal token]
```

这种方式更接近“给 SID 加 temporal suffix”。

#### Parallel Quantization

将 text/time 融合后的表示送入不同 encoder 或 codebook，使 item 语义与时间信号在量化层面有一定分离。

该方式在论文中表现较好，尤其是使用 relative time 时。

### 3.4 一个具体例子

假设同一个用户有如下序列：

```text
2024-01-01: iPhone case
2024-01-02: USB-C cable
2024-04-20: camping tent
```

对 `USB-C cable`：

```text
relative time gap = 1 day
```

对 `camping tent`：

```text
relative time gap = 109 days
```

即使两个 item 的文本语义不变，ChronoID 会把交互发生的时间节奏编码进 SID 或生成条件中，使模型区分短期连续兴趣和长间隔后的新兴趣。

### 3.5 对我们的启发与限制

ChronoID 的重要启发是：

```text
显式时间信息确实可能提升 generative recommendation。
```

但它不等价于证明：

```text
temporal suffix 应该成为 canonical item SID 的一部分。
```

本阶段形成的关键判断是：

```text
时间信息更适合作为 event/context token，而不是直接污染 item identity。
```

原因包括：

1. 同一个 item 在不同时间会拥有多个 temporal SID，候选去重复杂。
2. next-item prediction 时未来 item 的交互时间不一定已知。
3. search 和 rec 的时间语义不同，强行共享 temporal suffix 容易引入噪声。
4. canonical item SID 应尽量稳定，否则 refresh 和 checkpoint compatibility 更难处理。

因此，我们目前建议主方法使用：

```text
Search SID: [shared prefix | search suffix]
Rec SID:    [shared prefix | rec suffix]
```

时间信息作为输入条件：

```text
Rec input:
  <REC> user history + time context -> [P | R]

Search input:
  <SEARCH> query + time context -> [P | S]
```

ChronoID-style temporal suffix 可以作为 ablation：

```text
[shared prefix | task suffix | temporal suffix]
```

但不建议作为主方法。

## 4. SSRLive: Live Streaming Recommendation with Dynamic Semantic ID

### 4.1 任务设置

SSRLive 面向 live streaming recommendation。

它的核心特点是 item 状态高度动态：

```text
同一个主播 / 直播间在不同时间的内容、观众、热度、互动状态都可能快速变化。
```

因此，单一静态 SID 无法充分表达当前直播间状态。

### 4.2 Static SID + Dynamic SID

SSRLive 将 item 表示拆成两部分：

```text
static SID:
  表示主播 / 直播间的长期稳定属性

dynamic SID:
  表示当前直播内容、实时观众状态、短期兴趣信号
```

示意：

```text
streamer A:
  static SID = [12, 7, 31]

morning cooking stream:
  dynamic SID = [4, 18]

night gaming stream:
  dynamic SID = [9, 22]
```

同一个 streamer 的 static SID 可以保持稳定，而 dynamic SID 随直播内容变化。

### 4.3 动态更新

SSRLive 的 dynamic SID 依赖实时特征和动态 codebook，并使用类似 EMA 的方式更新 codebook 或动态表示。

它还采用 hybrid generative-discriminative pre-ranking：

```text
生成模型产生 static / dynamic SID 候选
判别模型结合多任务目标进行排序
```

### 4.4 对我们的启发与限制

SSRLive 对我们的启发是：

```text
把 item identity 拆成 stable component 和 dynamic component 是合理的。
```

这与我们的结构有相似直觉：

```text
shared prefix = 稳定、共享、低频更新部分
task suffix   = 任务相关、可局部更新部分
```

但 SSRLive 的边界是：

1. 它面向 live streaming recommendation，不是 search-rec。
2. 它的 dynamic SID 更偏 item 当前状态，不是 search 与 rec 共享结构中的任务冲突诊断。
3. 它没有处理 shared prefix 在两个任务之间是否应该更新的问题。

因此，它可以作为“stable + dynamic SID decomposition”的相关工作，但不能覆盖我们的核心问题。

## 5. 三篇论文的横向比较

| 工作 | 场景 | 核心 SID 思路 | 是否处理时间 | 是否处理 Search-Rec | 对我们的启发 |
| --- | --- | --- | --- | --- | --- |
| Mitigating SID Staleness | Generative recommendation | 重建 collaborative SID 并做新旧 token 对齐 | 隐式时间 block | 否 | SID refresh 需要 checkpoint compatibility |
| ChronoID | Generative recommendation | 显式时间信号注入 SID / 表示 | 是 | 否 | 时间信号有用，但不一定应成为 canonical item SID |
| SSRLive | Live streaming recommendation | static SID + dynamic SID | 是，实时状态 | 否 | stable/dynamic 分解合理 |

本阶段结论：

```text
这些工作都说明 dynamic / time-aware SID 是有价值的，
但都没有系统处理 unified search-recommendation 中 partially shared SID 的动态维护。
```

我们的差异化空间是：

```text
在 Search 与 Rec 共享 prefix、各自拥有 suffix 的结构下，
根据两个任务的漂移状态决定更新 prefix 还是 suffix，
并尽量保持旧 checkpoint 兼容。
```

## 6. SID 结构的阶段性决策

本阶段讨论后，建议主方法不要把 temporal suffix 直接放入 canonical item SID。

主结构仍然是：

```text
Search SID_i = [P_i | S_i]
Rec SID_i    = [P_i | R_i]
```

其中：

- `P_i`：shared prefix，表示 search 与 rec 共同需要的稳定 item 语义；
- `S_i`：search suffix，表示 query-item relevance、lexical/semantic matching 等 search-specific residual；
- `R_i`：rec suffix，表示 collaborative filtering、sequential transition、co-occurrence 等 rec-specific residual。

时间信息作为上下文条件：

```text
Rec event:
  <REC> <time/gap token> user history -> [P_i | R_i]

Search event:
  <SEARCH> <time token> query tokens -> [P_i | S_i]
```

这样做的优势是：

1. item identity 保持稳定；
2. 时间漂移仍可被建模；
3. 不会让同一个 item 产生多个 canonical SID；
4. 更容易做 SID refresh 和 checkpoint reuse；
5. temporal suffix 可以作为对照实验验证。

## 7. Prefix-share 与 Multi-task 的进一步理解

本阶段再次明确：

```text
Prefix-share 是结构设计。
Multi-task 是训练方式。
```

二者并不冲突。

更合理的组合方式是：

```text
multi-task learned shared prefix
+
task-residual suffix
```

也就是：

```text
Search SID_i = [P_i | S_i]
Rec SID_i    = [P_i | R_i]
```

其中 `P_i` 通过 search 和 rec 的共同信号学习，`S_i` 和 `R_i` 则只编码 shared prefix 解释不了的任务残差信息。

这种组合比 naive prefix-share 更合理，因为 naive prefix-share 可能导致：

```text
prefix 和 suffix 重复编码相同信息。
```

而 residual suffix 可以使结构更有解释性：

```text
prefix: 共同语义
suffix: 任务残差
```

## 8. 避免 Prefix 和 Suffix 信息重复

本阶段认为这是方法设计中的关键点。

如果没有约束，SID 可能退化为：

```text
prefix 已经编码了完整 item identity
suffix 再重复编码一遍 item identity
```

这样会导致：

- 局部刷新不再有效；
- prefix/suffix 的解释性下降；
- search/rec 冲突难以定位；
- prefix-share 结构无法体现优势。

可采用的机制包括：

### 8.1 Residual Learning

先学习 shared prefix，再让 suffix 只编码 prefix 解释不了的部分。

示意：

```text
suffix_input^S = z_i^S - g_S(P_i)
suffix_input^R = z_i^R - g_R(P_i)
```

然后：

```text
S_i = Q_S(suffix_input^S)
R_i = Q_R(suffix_input^R)
```

这是目前最推荐的实现方式。

### 8.2 Orthogonality / Decorrelation

约束 prefix 表示和 suffix 表示低相关：

```text
L_orth = || H_P^T H_S ||_F^2 + || H_P^T H_R ||_F^2
```

或：

```text
L_decorr = || Cov(P, S) ||_F^2 + || Cov(P, R) ||_F^2
```

### 8.3 Bottleneck and Masking

通过限制容量和训练方式减少重复：

```text
short prefix
short suffix
prefix dropout
suffix dropout
prefix-only decoding auxiliary loss
suffix residual reconstruction loss
```

### 8.4 Staged Training

实用训练流程：

```text
1. 先训练 shared prefix。
2. 冻结或半冻结 prefix。
3. 训练 search / rec suffix 去补充残差。
4. 最后小学习率联合微调。
```

## 9. 共同空间投影如何学习

因为 Search 与 Rec 的原始 embedding 空间可能不同，不能直接比较二者漂移方向。

本阶段提出先学习共同诊断空间：

```text
z_i^S -> W_S -> h_i^S
z_i^R -> W_R -> h_i^R
```

其中：

- `z_i^S`：item 在 search 侧的原始表示；
- `z_i^R`：item 在 rec 侧的原始表示；
- `W_S, W_R`：投影到共同空间的映射；
- `h_i^S, h_i^R`：共同空间中的 search / rec 表示。

### 9.1 Item-level alignment

同一个 item 的 search 表示和 rec 表示天然构成正样本：

```text
positive: (z_i^S, z_i^R)
negative: (z_i^S, z_j^R), j != i
```

可使用 contrastive loss：

```text
L_align = - log exp(sim(W_S z_i^S, W_R z_i^R) / τ)
          / Σ_j exp(sim(W_S z_i^S, W_R z_j^R) / τ)
```

### 9.2 Neighborhood-level alignment

为了让共同空间适合学习 shared prefix，还需要保持 item-item 结构：

```text
sim(h_i^S, h_j^S) ≈ sim(h_i^R, h_j^R)
```

可写成：

```text
L_struct = Σ_{i,j} || sim(h_i^S, h_j^S) - sim(h_i^R, h_j^R) ||^2
```

### 9.3 Multi-task supervised alignment

共同空间不能只做对齐，否则可能抹掉 search / rec 的有效差异。

推荐目标：

```text
L = L_search + L_rec + λ1 L_align + λ2 L_struct
```

共同空间主要用于：

```text
1. 学习 shared prefix；
2. 诊断 search / rec 是否发生同向漂移；
3. 决定更新 prefix 还是 suffix。
```

而 search / rec 的任务差异仍然保留给各自 suffix。

## 10. “两个任务同向变化”的定义

本阶段对“Search 与 Rec 两个任务同向变化”给出初步可操作定义。

在共同空间中，定义：

```text
h^S_{i,t} = W_S z^S_{i,t}
h^R_{i,t} = W_R z^R_{i,t}
```

漂移向量为：

```text
Δ^S_i = h^S_{i,t} - h^S_{i,t-1}
Δ^R_i = h^R_{i,t} - h^R_{i,t-1}
```

方向一致性：

```text
A_i = cos(Δ^S_i, Δ^R_i)
```

漂移强度：

```text
D^S_i = ||Δ^S_i||
D^R_i = ||Δ^R_i||
```

只有当：

```text
D^S_i > threshold_S
D^R_i > threshold_R
```

时，才有必要判断方向是否一致。

解释：

```text
A_i 接近 1：Search 与 Rec 同向漂移
A_i 接近 0：二者变化关系弱
A_i 接近 -1：二者冲突漂移
```

### 10.1 邻域变化一致性

除了单点向量，也可以比较 item 的邻域变化。

对 anchor item `i`，定义其相对其他 item 的相似度变化：

```text
v_i^S(j) = sim(h^S_{i,t}, h^S_{j,t}) - sim(h^S_{i,t-1}, h^S_{j,t-1})
v_i^R(j) = sim(h^R_{i,t}, h^R_{j,t}) - sim(h^R_{i,t-1}, h^R_{j,t-1})
```

邻域一致性为：

```text
A_neighbor = cos(v_i^S, v_i^R)
```

这表示两个任务是否都把 item 推向或远离同一批邻居。

### 10.2 Gradient agreement

也可以从训练目标角度判断 shared prefix 更新是否同时有利于两个任务：

```text
g^S = ∇_P L_search
g^R = ∇_P L_rec
```

梯度一致性：

```text
G = cos(g^S, g^R)
```

其中：

- representation agreement 更像数据语义漂移诊断；
- gradient agreement 更像更新 shared prefix 是否会同时帮助两个任务的优化诊断。

### 10.3 综合决策

可以定义综合分数：

```text
C_i = α A_i + β A_neighbor_i + γ G_i
```

然后根据漂移强度和一致性决定更新位置：

| Search 漂移 | Rec 漂移 | 一致性 | 更新策略 |
| --- | --- | --- | --- |
| 低 | 低 | - | 不更新 |
| 高 | 低 | - | 更新 search suffix |
| 低 | 高 | - | 更新 rec suffix |
| 高 | 高 | 高 | shared prefix 候选，可配合 suffix 微调 |
| 高 | 高 | 低或负 | 保持 prefix，分别更新 search suffix 和 rec suffix |

需要强调：

```text
同向变化只能作为 prefix refresh 的候选条件。
最终仍需要验证更新 prefix 后 search 和 rec 的 validation loss 是否同时改善。
```

另一个技术注意点是：

```text
embedding rotation 可能制造虚假漂移。
```

因此共同空间需要使用固定 encoder、anchor alignment 或稳定投影，避免把表示空间旋转误判为真实语义漂移。

## 11. 当前方法框架 v0

本阶段结束时，方法框架可以暂定为：

```text
1. 构造 Search / Rec 两侧 item 表示：
   z_i^S, z_i^R

2. 学习共同诊断空间：
   h_i^S = W_S z_i^S
   h_i^R = W_R z_i^R

3. 从共同空间量化 shared prefix：
   P_i = Q_P(f(h_i^S, h_i^R))

4. 用 residual learning 构造 task-specific suffix：
   S_i = Q_S(z_i^S - g_S(P_i))
   R_i = Q_R(z_i^R - g_R(P_i))

5. 得到两套任务 SID：
   Search SID_i = [P_i | S_i]
   Rec SID_i    = [P_i | R_i]

6. 时间信息作为输入条件，而不是 canonical SID 的一部分。

7. 在新时间窗口中诊断漂移：
   Search-only drift -> update S_i
   Rec-only drift    -> update R_i
   aligned drift     -> candidate update P_i
   conflict drift    -> keep P_i, update S_i / R_i separately

8. SID refresh 后进行 token alignment / light finetuning，保持 checkpoint compatibility。
```

## 13. 本阶段形成的核心判断

1. 纯 recommendation dynamic SID 已经有相关工作，不能作为主要 novelty。
2. Stale SID 工作强调 refresh 后的 checkpoint compatibility，这对我们很重要。
3. ChronoID 说明显式时间信号有价值，但不代表 temporal suffix 应成为 canonical item SID。
4. SSRLive 支持 stable + dynamic 分解思路，但没有处理 search-rec partially shared SID。
5. 我们的主结构仍建议为 `[shared prefix | task-specific suffix]`。
6. 时间信息建议作为 event/context token，而不是 item SID token。
7. Prefix-share 和 Multi-task 可以结合：multi-task shared prefix + task-residual suffix。
8. 避免 prefix/suffix 信息重复是关键技术点，residual suffix 是第一优先方案。
9. Search 与 Rec 的漂移方向比较需要先学习共同空间。
10. “两个任务同向变化”可以用 drift vector cosine、neighbor drift agreement 和 gradient agreement 共同定义。
11. prefix refresh 应该是保守操作：只有两个任务都明显漂移且方向一致时才考虑更新。
12. 如果两个任务都漂移但方向冲突，应保持 shared prefix，分别更新 search suffix 和 rec suffix。
