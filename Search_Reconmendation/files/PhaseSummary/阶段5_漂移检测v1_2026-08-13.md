# 阶段5：Temporal Drift 检测 v1（2026-08-13）

## 1. 本轮目的

在训练 temporal SID update 前，先确认 strict 20K 数据中是否存在可检测的自然 Search/Rec 漂移，并只用 t0 历史数据校准阈值。本轮不更新 SID，也不读取下游未来表现来调整 detector。

采用 prequential/test-then-train 协议：`W1` 先作为未来窗口评估，评估结束后才允许进入下一阶段 update；随后用更新后的状态评估 `W2`，以此类推。

## 2. 时间窗口

```text
B1 = 2011-01-01 ~ 2011-06-30
B2 = 2011-07-01 ~ 2011-12-31
B3 = 2012-01-01 ~ 2012-06-30
B4 = 2012-07-01 ~ 2012-12-31

W1 = 2013-01-01 ~ 2013-06-30
W2 = 2013-07-01 ~ 2013-12-31
W3 = 2014-01-01 ~ 2014-07-23
```

`B1-B4` 只用于估计 t0 正常抽样波动，`W1-W3` 不参与阈值拟合。

| Window | Search events | Search items | Rec events | Rec items |
|---|---:|---:|---:|---:|
| B1 | 5,057 | 2,475 | 8,212 | 3,343 |
| B2 | 7,194 | 3,144 | 11,667 | 4,240 |
| B3 | 8,129 | 3,667 | 13,381 | 4,979 |
| B4 | 11,607 | 4,785 | 19,277 | 6,369 |
| W1 | 18,109 | 6,343 | 30,547 | 8,386 |
| W2 | 14,500 | 5,614 | 25,756 | 7,747 |
| W3 | 9,210 | 4,150 | 17,676 | 6,150 |

## 3. 指标与阈值

Search 指标：

```text
query_js                 query 频率分布 JS divergence
query_mmd                frozen BGE query embedding 分布 MMD
item_query_centroid      同 item 的 query centroid cosine shift
```

Rec 指标：

```text
popularity_js            item 流行度分布 JS divergence
transition_js            item 条件转移分布的 support-weighted JS
neighbor_jaccard_drift   top-20 sequence neighbor 的 1-Jaccard
```

阈值使用 1,000 次 user-block bootstrap。对每个相邻参考窗口，先合并左右 user-window blocks 并移除时间标签，再独立采样为左右组；这样 null 只包含采样波动，不把 B1→B2 的真实时间变化错误纳入正常波动。

三个相邻参考窗口共得到每项 3,000 个 null 样本。主阈值为 pooled null 的 95% 分位数：

| Task | Metric | Null median | q90 | q95 | q99 |
|---|---|---:|---:|---:|---:|
| Search | query JS | 0.02733 | 0.03408 | **0.03509** | 0.03666 |
| Search | query MMD | 0.0000968 | 0.0001495 | **0.0001685** | 0.0002199 |
| Search | item-query centroid | 0.001115 | 0.001756 | **0.001993** | 0.002554 |
| Rec | popularity JS | 0.20309 | 0.21970 | **0.22210** | 0.22565 |
| Rec | transition JS | 0.55366 | 0.58307 | **0.59374** | 0.61098 |
| Rec | neighbor drift | 0.69957 | 0.72198 | **0.72807** | 0.73838 |

任务触发规则：三个 p-value 在任务内做 BH-FDR 0.05；至少两个指标显著，且 relation-level 指标显著。Search relation 指标为 item-query centroid，Rec relation 指标为 transition JS。

## 4. Natural Drift 结果

### Search

| Pair | query JS | query MMD | item-query centroid | BH significant | Trigger |
|---|---:|---:|---:|---|---|
| B4→W1 | 0.04321 | 0.0003486 | 0.000666 | JS, MMD | **No** |
| W1→W2 | 0.04110 | 0.0001689 | 0.000788 | JS | **No** |
| W2→W3 | 0.03518 | 0.0001760 | 0.001160 | none after BH | **No** |

Search 的整体 query mix/语义分布有变化，但相同 item 关联 query 的 centroid 没有超过正常波动，因此当前数据不支持自然 Search suffix 更新。这与 pseudo-query 数量少、类别模板较粗有关。Search-only drift 后续必须加入 controlled stress test。

### Rec

| Pair | popularity JS | transition JS | neighbor drift | BH significant | Trigger |
|---|---:|---:|---:|---|---|
| B4→W1 | 0.32314 | 0.83963 | 0.98248 | all | **Yes** |
| W1→W2 | 0.32101 | 0.81367 | 0.98159 | all | **Yes** |
| W2→W3 | 0.31111 | 0.84311 | 0.98083 | all | **Yes** |

Rec 在三个连续窗口中均显著漂移，因此第一轮 SID update 选择 `B4→W1 Rec-only natural drift`。

需要注意，transition 和 neighbor 指标绝对值很高，反映半年窗口 item transition 非常稀疏；任务级显著性成立，但 item 更新集合不能只依据 neighbor Jaccard。

## 5. Item-Level 支持度诊断

候选 item 先要求两个窗口中均至少 5 次 item interaction、至少 3 次 outgoing transition：

| Pair | Union items | Eligible items | Eligible ratio | Top-30% diagnostic |
|---|---:|---:|---:|---:|
| B4→W1 | 10,482 | 367 | 3.50% | 111 items |
| W1→W2 | 11,407 | 522 | 4.58% | 157 items |
| W2→W3 | 9,958 | 392 | 3.94% | 118 items |

Top-30% 只是按 popularity log-ratio 与 transition-JS 形成的候选排序，不能作为最终统计阈值。正式 item selector 需要按 support bucket 做 null bootstrap，并比较：

```text
all eligible update       作为自然漂移可恢复上限
bootstrap selective update 作为主方法
top-k update              作为固定预算对照
```

## 6. 下一步实验

1. 从 `<=2012-12-31` 的累计行为重新训练真正的 t0 UniSAR、v13b prefix/suffix 和 GenSAR baseline，不能复用读取到 2014 年行为的静态模型。
2. 以 W1 为首次未来窗口，在更新前评估 t0 模型。
3. W1 评估完成后，用 W1 Rec 行为更新 Rec representation。
4. 固定 prefix 和 Search suffix，比较 No-update、Reassign-only、Adapter-only、Adapter+Codebook 与 Full retrain。
5. 对 Adapter-only 同时比较 all-eligible、bootstrap-selective 与相同数量 random item。
6. 使用更新后的模型评估 W2，然后将 W2 转为下一轮 update 数据，形成连续 test-then-train。
