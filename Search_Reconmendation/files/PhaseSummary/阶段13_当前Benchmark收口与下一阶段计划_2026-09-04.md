## 2. 当前最终方法

当前可用版本记为：

```text
Impact-aware Selective Task-local SID Update
```

SID 结构：

```text
[shared prefix: 2 codes | Search/Rec suffix: 2 codes]
codebook size = [256, 256 | 256, 256]
```

Rec drift 时：

- prefix、Search suffix 和所有 codebook 固定；
- detector 按 `drift_rank_score * sqrt(current_events)` 排序；
- 要求 `current_events >= 5`；
- 固定选择 K=51 个 item；
- 只训练 14,528 个 Rec-adapter 参数；
- 加入 2 倍 replay item；
- 用 sticky ratio 0.1 决定是否实际换码；
- 未选 item 的 operational SID 严格保持不变。

## 3. 已经成立的结果

### 3.1 W6 三 seed

| 方法 | Rec nDCG@10 | Search nDCG@10 |
|---|---:|---:|
| Fixed | 0.019476 | 0.021221 |
| SupportTopK | 0.019914 | 0.021322 |
| V3 | **0.020050** | **0.021408** |

V3 相比 Fixed：

- Rec nDCG@10 平均提升 0.000574，3/3 seed 正向；
- Search nDCG@10 平均提升 0.000187，3/3 seed 正向。

### 3.2 W9 留出窗口

| 方法 | Rec nDCG@10 | Search nDCG@10 |
|---|---:|---:|
| Fixed | 0.018533 | 0.028408 |
| Random | 0.019149 | 0.028481 |
| SupportTopK | **0.019477** | 0.028611 |
| V3 | 0.019464 | **0.028723** |

V3 在 W9 仍明显优于 Fixed 和 Random，Search 未退化；Rec 与 SupportTopK 基本持平。

### 3.3 SID 稳定性与成本

- W6/W9 只选择 51/19,999 个 item，实际换码 33/36 个；
- 完整 SID duplicate fraction 保持在约 0.4%；
- prefix、另一任务 suffix 和未选 item SID 均保持不变；
- W6 selective adapter 为 4.60 秒，全 item adapter 成本下界为 25.77 秒；
- 全 item adapter 原始换码 86.7%，并产生明显更高 collision。

因此，“以较低成本局部更新 SID，并保持未漂移任务稳定”这一核心机制已经得到支持。

## 4. 尚未解决的问题

### 4.1 Detector 尚未稳定优于 SupportTopK

W6 上 V3 相比 SupportTopK 的 Rec nDCG@10 为 2/3 seed 正向，W9 则低 0.000013。当前证据不足以声称 detector 本身稳定优于高支持量启发式。

### 4.2 Emerging item 被检测到，但新 SID 没有被下游充分学会

W9 中 V3 覆盖的注入 target 事件明显多于 SupportTopK，但 V3-only 实际换码的 19 个 item 在 W10 有 83 条测试样本，四个方法的 nDCG@10 都为 0。

这说明当前瓶颈已经不完全在 SID detector，而在：

```text
发生换码 -> 下游模型获得的新 SID 对齐监督太少 -> 新 SID 无法稳定生成
```

### 4.3 成本优势还不完整

当前只测了 SID adapter 阶段。下游仍完整训练 T5-small 一轮，因此还没有实现端到端的低成本 temporal adaptation。

## 5. 下一阶段核心问题

下一阶段不应继续在 W9 调 detector，而应回答：

> 如何让少量发生变化的 SID 被下游生成模型快速学会，同时保持总训练预算、旧 item 和另一任务性能稳定？

建议将下一版本记为：

```text
Changed-item-aware Alignment v2
```

## 6. 下一阶段实验计划

### P0：冻结当前 benchmark

在开始新实验前固定：

- detector v3 公式；
- K=51；
- sticky ratio=0.1；
- codebook size 和 SID length；
- W6 为 development window；
- W9 结果只作为已有证据，不继续用于超参选择。

本步骤只需要写配置清单和运行 manifest，不重新训练。

### P1：Changed-item-aware Alignment v2

只在 W6 development window 上开发，保持每组 alignment 总预算相同。

建议依次比较：

| 方案 | 内容 | 目的 |
|---|---|---|
| A0 | 当前每个 alignment item 一次 Item2Index/Index2Item | 原始基线 |
| A1 | 对实际 recoded item 重复 2/4/8 次，减少普通 fill item | 判断是否只是监督密度不足 |
| A2 | A1 + `old SID -> new SID` transition task | 显式教模型 SID 发生了局部变化 |
| A3 | A2 + unchanged/Search replay distillation | 控制旧 item 和 Search 遗忘 |

公平性约束：

- Fixed、Random、Support、V3 的总 alignment 样本数相同；
- 各方法只对自己的实际 recoded item增加重复监督；
- 减少相同数量的随机 fill item，不能额外增加 V3 总训练量；
- 初始 checkpoint、seed、epoch 和训练任务保持一致。

P1 第一轮只跑 seed 2024。若 A1/A2 不能让 W6 的 recoded-item 子集明显改善，停止复杂化，不继续 A3。

### P2：Selective downstream adapter

如果 P1 证明 changed-item alignment 有效，再将下游完整 T5 更新替换为 LoRA/adapter：

- 只训练 task-local LoRA/adapter；
- 保留 changed-item alignment 和 replay；
- 比较完整 T5 update 与 selective downstream update 的效果、时间和显存；
- 报告端到端成本：representation、SID adapter、物化、下游更新四部分。

目标不是要求 LoRA 绝对优于完整 T5，而是在性能下降可控时获得明确成本优势。

### P3：第二个 benchmark

完成 P1 的结构选择后再迁移，避免同时改变方法和数据。

建议优先级：

1. **第二个 Amazon domain + 同一 pseudo-search pipeline**：保留 Search+Rec 联合任务和完整可控实验协议，最适合作为跨域验证；
2. **KuaiRand/类似自然行为流数据**：用于补充自然 Rec drift，但缺少原生 Search，只能作为 Rec-only 外部验证；
3. 如果能获得公开的真实 joint search-rec 日志，再作为最强外部 benchmark。

第二 Amazon domain 应满足：

- metadata/title/description 相对完整；
- item 和交互规模足够构造季度窗口；
- query 容易从 metadata 或 review 文本构造；
- 与 Electronics 的类别和消费模式有明显差异。

可优先评估 `Sports_and_Outdoors` 与 `Home_and_Kitchen`，最终选择一个数据质量更好的 domain。

### P4：最终论文实验矩阵

只有 P1/P2 通过后再扩展：

- Rec-only drift；
- Search-only drift；
- Search+Rec 同向与冲突漂移；
- 不同 drift intensity；
- 多 seed；
- 第二 domain/benchmark；
- 质量、collision、稳定性和端到端成本。

## 7. 下一步的停止/继续门槛

P1 在 W6 seed 2024 上满足以下条件才进入 P2：

1. V3 recoded-item 子集 nDCG@10 相比 A0 明显提高；
2. 整体 Rec 不低于当前 V3；
3. Search 相对下降不超过 1%；
4. 相同 alignment 总预算；
5. collision、换码 item 数与 SID mapping 完全不变。

随后至少用三个 seed 验证选中的 alignment 方法。若仍不能稳定优于 SupportTopK，应将论文贡献重点放在“task-local、低成本、稳定更新”，而不是强调 detector 排序优越性。
